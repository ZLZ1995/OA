# 操作类底稿并行审核：实现与部署说明

## 2026-10-29 检测问题修复执行方案

1. F1：保留现有项目删除权限与语义；删除时先清理底稿文件关联、提交轮次、审核主记录，再清理工单；文件物理删除延迟到事务提交后。启动发现底稿孤儿记录时阻止启用，避免无声继承。验收覆盖删除后重新建项目及事务回滚。
2. F2：基线仅初始化尚无版本的存量项目；功能启用后创建的项目明确写入新版本，重启保持已经冻结的版本。未知版本拒绝启动。旧清单不重抓、不按阶段重划。验收覆盖最高项目ID删除、复用、重启。
3. F3：外部三审撤回允许新的并行等待状态；与底稿通过使用同一工单锁，撤回不修改底稿状态。验收两种执行先后及原权限限制。
4. F4：前端按“工单+当前轮次+可编辑状态”建立新的提交标识；同一次重试保持标识。后端禁止将已撤回/退回轮次的旧标识当成新的提交成功。验收响应丢失后撤回重提、改资料重提及正常幂等重试。
5. F5：后台每小时回收超过24小时且没有任何提交引用的临时ZIP；回收与提交使用同一工单锁，提交后才删除实体文件。前端同页即时清理保留。验收过期、未过期、有历史引用及并发提交。
6. 最后执行后端完整测试、前端测试及严格构建，并更新验收记录。开发阶段未推送；后续发布按用户的单独上线授权执行。

## 数据与事务

- `projects.workflow_version`：LEGACY或PARALLEL_WORKPAPER_V1，初始化后不可改变。空值仅代表尚未启用的兼容安装。基线只初始化空值；启用后新建项目显式写入PARALLEL_WORKPAPER_V1，重启保留已持久化版本，即使SQLite复用了清单中的数字ID也不重新划为旧流程。
- `operation_workpaper_reviews`：每工单一条，状态、当前提交轮次和revision。
- `operation_workpaper_submissions`：保留每轮提交人、指定审核人、资料类型、网盘信息、提交/进入/撤回/决定时间与理由。
- `operation_workpaper_submission_files`：引用文件，不复制历史文件实体。
- `work_orders.operation_workpaper_reviewer_id`：当前审核职责，用于停用账号交接及相关项目检索。

状态：二审通过建立DRAFT；提交变SUBMITTED；进入审核页变IN_REVIEW，或在进入前撤回变WITHDRAWN；审核通过APPROVED或退回REJECTED。WITHDRAWN/REJECTED重提创建新轮次，不复用旧轮次。revision与current_submission_id参与条件更新，撤回和进入只能有一个成功。重复request_id只接受相同资料。业务操作、工作流日志及通知一起提交。

三审不共享底稿状态或当前办理人。第三轮通过（或外部复核完成）准备进入签发时，底稿未通过则转WAIT_PARALLEL_WORKPAPER；底稿通过后回到WAIT_OWNER_SIGNOFF_UPLOAD。签发进入和通过接口仍独立检查两项结果，防止绕过页面限制。审核人停用的底稿交接不阻断三审，重新分配保留进入时间。

## 接口与页面

接口前缀 `/api/v1/operation-workpapers`：

| 方法与路径 | 行为 |
|---|---|
| GET /tasks | 本人底稿待办，不触发进入 |
| GET /work-orders/{id} | 状态及历史；未进入的审核人不返回资料 |
| GET /work-orders/{id}/candidates | 负责人选择档案管理员，可选自己 |
| POST /work-orders/{id}/files | 负责人上传有效ZIP，流式写入 |
| DELETE /files/{id} | 仅删除未被任何轮次引用的临时文件 |
| POST /work-orders/{id}/submit | XOR资料校验、revision校验、幂等提交 |
| POST /submissions/{id}/enter | 仅本轮指定审核人进入，记录时间 |
| POST /submissions/{id}/withdraw | 仅负责人且SUBMITTED状态可撤回 |
| POST /submissions/{id}/decision | 仅指定审核人，退回理由必填 |

前端在明确打开“操作类底稿审核”面板时调用enter，普通项目页、提交面板不调用。负责人即使具有档案管理员角色，查看提交面板也不会失去撤回权。文件下载保留鉴权；普通文件列表不暴露底稿，通用上传/替换/删除不能绕开专用审核接口。

## 部署顺序

1. 保留当前生产数据库与文件卷的可恢复备份；本次开发阶段未修改生产库。
2. 将原始快照以只读文件挂载到后端，例如 `/data/workflow/legacy-project-baseline.json`。不要放入前端资源、镜像公开层或Git。
3. 只读验证：在backend目录运行 `python scripts/verify_workflow_baseline.py /data/workflow/legacy-project-baseline.json --service-id 69e06fdf345a78e2a2f77517`。
4. 在维护窗口停止旧版本写入，运行迁移0007（SQLite应用启动亦会补齐字段及建表）。配置 `OA_WORKFLOW_BASELINE_PATH` 为挂载文件，`OA_WORKFLOW_SOURCE_SERVICE_ID` 为上述原始服务ID。迁移到其他主机时仍使用同一快照来源ID，不重新划分项目。
5. 后端初始化按快照固定尚未赋值的项目版本，已赋值项目不重新分类。快照缺失、损坏、环境不符、未知版本或底稿审核孤儿记录均禁止启用。新流程已启用后不能移除配置，即使DB_INIT_REQUIRED=false也会停止启动。
6. 快照后、部署前新建的项目仍属于新流程；若已二审通过，补建底稿待提交状态；若已经越过签发门槛，初始化拒绝启动并给出项目ID，不能擅自当成旧项目或破坏已完成记录。应在部署前只读预检并处理这一真实数据差异。
7. 部署前后端同一版本，用测试账号验证下列验收；最后再恢复写入。回滚保留新增审核记录，不能直接降级删除新表；若需要恢复数据库，必须同时处理维护窗口后新增数据，不能覆盖丢失。

## 验收

- 清单内项目覆盖各流程状态，全部LEGACY，无新增底稿待办或签发门槛。
- 新项目二审通过后生成独立待办，三审办理人不变。
- ZIP多文件、网盘链接+提取码分别成功；两者同时、空资料、假ZIP、跨项目文件均拒绝。
- 有档案管理员角色的负责人可自审；非指定审核人、其他项目人员不能进入或下载。
- 负责人查看提交页面不锁定；指定审核人进入审核页立即锁定；刷新不重置时间。
- 两个数据库连接同时进入/撤回，仅一个成功；旧轮次入口失效。
- 退回理由空白拒绝；补充后新轮次可再次撤回；保留历史记录。
- 两种通过先后顺序均能汇合；只通过一项不能签发；外部审核分支保持原规则。
- 审核人员停用进入管理员交接清单，可重新分配给具备角色的负责人，进入时间不重置。
- 现有后端测试、前端类型检查、构建与界面联调通过后才发布。

| F5 | workpaper_temporary_files与main生命周期定时任务 | 过期且无引用才回收、历史引用保留、回滚保留、提交先取得锁后回收重新检查 |

临时文件维护：服务启动后即执行一次，随后每小时执行；每次最多500条，超过24小时且无任何历史提交引用才可删除。不扫描任意目录，不删除上传中的文件；提交接口会拒绝已经过期清理的文件ID，负责人可重新选择上传。物理删除失败记录错误日志供运维排查。已纳入审核历史的文件不受此临时回收策略影响。

项目删除沿用现有业务删除语义，审核数据在项目正式删除时一并删除；仅撤回或退回底稿不会删除历史。新增检查不会自动清除来源不明的孤儿审核数据，遇到此类数据应先备份并核对来源。

修复后验收结果：后端完整测试232项通过（含14项新增检测问题回归）；前端10项测试通过；严格类型检查与生产构建通过；差异空白检查通过。检测报告保留原始发现并补充修复状态。当前仍为本地工作树修改，未提交、推送或部署。
